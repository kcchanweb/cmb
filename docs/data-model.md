# Event storage schema

Status: initial source-event fields reviewed by the user, with the explicit addition of a UUID row identifier. The original request to build the schema resumes after that field review. This bounded implementation creates only source-event storage and migration metadata; delivery state, replay/concurrent dispatch ownership, profile tables, and the incoming HTTP contract remain separate open work.

## Schema authority and migration

The authoritative DDL is [001_create_events.sql](../app/db/migrations/001_create_events.sql), run explicitly with make db-migrate from the project root. The command executes psql as event_relay_app inside db; credentials are not printed. The migration is transactional, takes a transaction-scoped advisory lock to serialize migration invocations, and records its version in public.schema_migrations so repeating it is a no-op. Do not modify applied migration files; add a new version. No third-party migration framework or PostgreSQL extension is added.

The reviewed fields came from the README source event, not the vendor's normalized example. The user supplied “We need to add a uuid for the table; the rest looks fine.” UUID identity is therefore a separate internal key; source messageId remains the stable deduplication identity.

## public.events

| Source field | Database column | SQL type | Nullability / default / constraints |
| --- | --- | --- | --- |
| New internal identifier | id | uuid | Primary key; generated by gen_random_uuid() when omitted |
| type | event_type | text | Required; nonblank; not restricted to a track/screen enum |
| event | event_name | text | Required; nonblank; source name preserved |
| messageId | message_id | text | Required; nonblank; globally unique for this single-source POC |
| timestamp | occurred_at | timestamptz | Required; finite instant; never substituted from receivedAt |
| receivedAt | received_at | timestamptz | Nullable; finite when present; no server-time default |
| userId | user_id | text | Nullable; nonblank when present; preserves numeric strings or UUID strings |
| deviceId | device_id | text | Required; nonblank |
| properties | properties | jsonb | Nullable when absent; must be an object when present |
| context | context | jsonb | Nullable when absent; must be an object when present |

Text identifiers are not restricted to UUID syntax: an incoming messageId may be a value such as msg_9988776655. The database generates only id; never replace message_id/device_id with it. UUID and numeric user IDs are stored as text, with profile resolution deferred to application logic; missing lookup entries do not violate a foreign key.

The selected minimal storage nullability is permissive for receivedAt, properties, and context because the full incoming contract has not fixed them as mandatory. Missing objects use SQL NULL; an explicit JSON null, array, or scalar fails the object check. Empty objects remain distinct from missing objects. Times represent instants and preserve fractional precision supported by PostgreSQL; original ISO-string formatting/offset text is not retained. No ordering constraint relates occurred_at and received_at because arrivals are out of order and client clocks may differ.

properties keeps event-specific values (purchase revenue/currency/sku, screen names, target profile IDs, and other event properties). context keeps the reviewed app/device/OS/locale object without splitting every nested field into a column. There is no raw-payload or traits column in this slice. Registration email/phone are not added as separate retained fields. context can contain advertising identifiers, so it is sensitive persisted input: keep the DB private, use the application role, and do not log or forward raw context. Production retention/deletion/access policy remains open.

## Constraints, indexes, and deduplication

The primary-key index on id supports internal references. The unique constraint/index on message_id is the database concurrency boundary for repeated event insertion. Only these two indexes are added: no JSONB GIN index or user/time index is justified without an actual query requirement. UUID generation uses PostgreSQL's built-in [UUID function](https://www.postgresql.org/docs/18/functions-uuid.html), and object fields use [JSONB](https://www.postgresql.org/docs/18/datatype-json.html).

Future intake must use an atomic insert/conflict path and distinguish same-ID/same-content from same-ID/different-content. A unique key alone does not prevent duplicate vendor calls or implement delivery/recovery ownership. This schema does not authorize UPDATE-overwriting an accepted event on conflict. No source events are forwarded by schema creation or schema tests.

The storage table permits any nonblank source event name, independently of the seven-name vendor allowlist. This avoids making persistence depend on a destination contract; it does not decide whether the incoming API accepts/stores ineligible events. Application eligibility gates must still prevent those events from reaching the vendor.

## Migration metadata and operational safety

public.schema_migrations contains version text PRIMARY KEY and applied_at timestamptz DEFAULT CURRENT_TIMESTAMP. It is operational metadata, not an incoming event table; its version key is not an event identifier. The migration checks version after acquiring the advisory lock. If events already exists without the recorded migration, CREATE TABLE fails and the transaction rolls back instead of silently accepting schema drift. Migration lock timeout is 5 seconds and statement timeout is 30 seconds. A later migration must handle any desired data/model changes explicitly.

make up still bootstraps only the database role and health skeleton. Use make db-migrate after startup; do not rely on docker-entrypoint-initdb.d to upgrade existing volumes. No destructive automatic down migration is supplied. Ordinary shutdown preserves all event data and the database volume. Initial DDL is additive; errors are rolled back atomically.

## Verification scope

make test-db requires the running database and an applied migration. A disposable test container uses the same pinned Node/pg dependencies and Compose network as api; its image is separate from the normal API image and its healthcheck is disabled. The regression script runs against the real PostgreSQL container, inserts synthetic events inside one transaction, and rolls everything back in finally. It verifies generated/distinct UUIDs, non-UUID message IDs, preserved numeric/UUID/anonymous users, JSON object/timestamp round trips, duplicate message-ID rejection, primary-key rejection, required/nonblank fields, invalid object shapes, and infinite time rejection. Re-running db-migrate verifies the version guard. No event HTTP API, delivery ledger, vendor sends, or full replay behavior is implemented by this schema slice.

Actual verification: the initial migration applied in an isolated database; repeating it was a no-op with exactly one version entry. All 24 schema checks passed there and then against the applied POC schema. Test rows were rolled back; the isolated database was removed. The running POC has the events table and migration metadata, with no seeded source data or vendor sends. /ready remained healthy after migration. Configuration of the base/test Compose files is part of the schema test workflow; infrastructure API behavior remains unchanged.
