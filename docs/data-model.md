The command executes psql as event_relay_app inside db; credentials are not printed. The migration is transactional, takes a transaction-scoped advisory lock to serialize migration invocations, and records its version in public.schema_migrations so repeating it is a no-op. Do not modify applied migration files; add a new version. No third-party migration framework or PostgreSQL extension is added.

The reviewed fields came from the README source event, not the vendor's normalized example. The user supplied “We need to add a uuid for the table; the rest looks fine.” UUID identity is therefore a separate internal key; source messageId remains the stable deduplication identity.

## public.events

| Source field | Database column | SQL type | Nullability / default / constraints |
| --- | --- | --- | --- |
| New internal identifier | id | uuid | Primary key; generated by gen_random_uuid() when omitted |
| type | event_type | text | Required; nonblank; not restricted to a track/screen enum |
| event | event_name | text | Required; nonblank; source name preserved |
| messageId | message_id | text | Required; nonblank; globally unique for this single-source POC |
| timestamp | occurred_at | timestamptz | Required; finite instant; never substituted from receivedAt |
| receivedAt | received_at | timestamptz | Nullable; finite when present; no server-time default |
| userId | user_id | text | Nullable; nonblank when present; preserves numeric strings or UUID strings |
| deviceId | device_id | text | Required; nonblank |
| properties | properties | jsonb | Nullable when absent; must be an object when present |
| context | context | jsonb | Nullable when absent; must be an object when present |

Text identifiers are not restricted to UUID syntax: an incoming messageId may be a value such as msg_9988776655. The database generates only id; never replace message_id/device_id with it. UUID and numeric user IDs are stored as text, with profile resolution deferred to application logic; missing lookup entries do not violate a foreign key.

The selected minimal storage nullability is permissive for receivedAt, properties, and context because the full incoming contract has not fixed them as mandatory. Missing objects use SQL NULL; an explicit JSON null, array, or scalar fails the object check. Empty objects remain distinct from missing objects. Times represent instants and preserve fractional precision supported by PostgreSQL; original ISO-string formatting/offset text is not retained. No ordering constraint relates occurred_at and received_at because arrivals are out of order and client clocks may differ.

properties keeps event-specific values (purchase revenue/currency/sku, screen names, target profile IDs, and other event properties). context keeps the reviewed app/device/OS/locale object without splitting every nested field into a column. There is no raw-payload or traits column in this slice. Registration email/phone are not added as separate retained fields. context can contain advertising identifiers, so it is sensitive persisted input: keep the DB private, use the application role, and do not log or forward raw context. Production retention/deletion/access policy remains open.

## Constraints, indexes, and deduplication

The primary-key index on id supports internal references. The unique constraint/index on message_id is the database concurrency boundary for repeated event insertion. Only these two indexes are added: no JSONB GIN index or user/time index is justified without an actual query requirement. UUID generation uses PostgreSQL's built-in [UUID function](https://www.postgresql.org/docs/18/functions-uuid.html), and object fields use [JSONB](https://www.postgresql.org/docs/18/datatype-json.html).

Implemented intake uses an atomic insert/conflict path and distinguishes same-ID/same-content from same-ID/different-content. The unique key is paired with delivery ownership below; uniqueness alone would not prevent duplicate vendor calls. This schema does not authorize UPDATE-overwriting an accepted event on conflict. No source events are forwarded by schema creation or schema tests.

The storage table permits any nonblank source event name, independently of the seven-name vendor allowlist. This avoids making persistence depend on a destination contract; it does not decide whether the incoming API accepts/stores ineligible events. Application eligibility gates must still prevent those events from reaching the vendor.

## Migration metadata and operational safety

public.schema_migrations contains version text PRIMARY KEY and applied_at timestamptz DEFAULT CURRENT_TIMESTAMP. It is operational metadata, not an incoming event table; its version key is not an event identifier. The migration checks version after acquiring the advisory lock. If events already exists without the recorded migration, CREATE TABLE fails and the transaction rolls back instead of silently accepting schema drift. Migration lock timeout is 5 seconds and statement timeout is 30 seconds. A later migration must handle any desired data/model changes explicitly.

make up now starts the DB, invokes make db-migrate for001/002, then starts the API. make db-migrate is also available explicitly; do not rely on docker-entrypoint-initdb.d to upgrade existing volumes. No destructive automatic down migration is supplied. Ordinary shutdown preserves all event data and the database volume. Initial DDL is additive; errors are rolled back atomically.

## Direct-delivery extension for the requested API

Implemented [migration002](../app/db/migrations/002_event_deliveries.sql), preserving applied001. public.event_deliveries has event_id UUID PRIMARY KEY/FK to events, source_hash SHA256, frozen allowlisted vendor_payload JSONB (NULL only for skipped events), status, attempts, current lease_token/lease_expires_at, last_http_status/error_code, and timestamps. Events and the initial delivery row commit in one transaction. Dispatch claims are short atomic updates and are never transactions held across HTTP. Token-guarded outcome writes prevent stale owners overwriting current state. Legacy source rows without a delivery record are not auto-backfilled or resent. The POC FK restricts deletion; retention/deletion policy remains future work.

This is minimal durable delivery state, not an outbox consumer, queue, or scheduler. Explicit retry/status HTTP endpoints provide recovery; terminal unchanged400/422 failures are not retried automatically or through the retry route.

## Implemented delivery identity and lifecycle

One event_deliveries row belongs to each newly accepted events row. Its event_id PK/FK is the internal UUID. source_hash is SHA256 of canonical retained source fields; traits are discarded before hashing, timestamps normalize to UTC with microseconds preserved, and JSON object key order is canonical. A same-ID/different-retained-content request returns409. Pre-existing events without a delivery record are protected as409 reconciliation cases, not silently resent.

vendor_payload is a frozen allowlisted JSONB snapshot, NULL only for skipped events. status is constrained to pending/sending/delivered/skipped/retryable_failed/permanent_failed/uncertain. attempts counts durable attempt intentions cumulatively across requests. last_http_status/error_code are safe numeric/category data; no raw vendor body is stored. created_at/updated_at/last_attempt_at/delivered_at are server instants. delivered_at is set only for confirmed delivered; a sending row requires a lease token/expiry, and other states clear them.

A short atomic UPDATE claims eligible work with a random UUID token and60-second lease. Each HTTP attempt checks the current unexpired token and increments attempts in a committed operation. Outcome updates also require the current token; stale handlers cannot overwrite a new owner. No transaction, row lock, or checked-out transaction connection spans HTTP/backoff. Transaction timeout5seconds and lock timeout1second protect intake; normal queries retain configured pool/query bounds. Existing records are immutable through the API; there is no delete/update endpoint. FK deletion is RESTRICT until a retention policy is defined.

The explicit retry route reuses snapshots and recovers pending/expired claims. A source event/delivery record commits before forwarding; failed/unknown commit prevents forwarding. Accepted HTTP followed by failed outcome recording retains sending/uncertain state and is recoverable after lease expiry. Database-backed claims prevent ordinary concurrent/duplicate dispatch, but external vendor idempotency is still required for ambiguous replay windows. No scheduler, queue or auto-retry after response is introduced.
